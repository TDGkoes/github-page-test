# GHCP Harness Agent Hands-on Lab

> 이 실습은 업무용 에이전트 하네스의 구성 원리와 검증 방법을 익히기 위한 안내서입니다. 실제 고객명, 원본 RFP, 사내 산출물, 계정 정보는 사용하지 않습니다. 메뉴와 기능 이름은 제품 버전에 따라 다를 수 있습니다.

## 실습 목표

실습을 마치면 다음을 할 수 있습니다.

- 에이전트 지침, Skill, 도구, Knowledge, 채널의 역할을 구분합니다.
- 에이전트가 요청을 해석하고 적절한 Skill을 선택하도록 구성합니다.
- Skill을 독립적으로 재사용할 수 있도록 목적, 입력, 절차, 검증 기준을 정리합니다.
- 합성 데이터로 정상 흐름과 예외 흐름을 테스트하고 결과를 평가합니다.
- 민감 정보와 미확정 정보를 안전하게 다루는 기준을 적용합니다.

## 하네스 구성 개념

하네스는 모델 하나가 아니라, 에이전트가 일관되게 일하도록 둘러싼 실행 환경입니다. 이 LAB에서는 각 구성요소의 책임을 겹치지 않게 나눕니다.

| 구성요소 | 책임 | 설계 팁 |
|---|---|---|
| Agent instructions | 역할, 공통 원칙, 요청 분류, Skill 선택·연결 | 공통 규칙과 라우팅만 둡니다. 작업별 상세 절차를 복사하지 않습니다. |
| Skill | 특정 업무의 입력, 수행 절차, 제약, 출력, 검증 | 한 Skill은 하나의 뚜렷한 업무 목적을 맡게 합니다. |
| Tool | 검색, 계산, 파일 생성 등 실제 동작 | 목적에 필요한 도구만 연결하고 권한을 최소화합니다. |
| Knowledge | 신뢰할 수 있는 참고 자료 | 최신성, 소유자, 접근 범위가 확인된 자료만 둡니다. |
| Channel | 사용자가 에이전트와 만나는 접점 | 게시 대상과 데이터 경계를 먼저 확인합니다. |
| Memory | 대화 간 맥락 유지(지원되는 경우) | 보존할 정보와 보존하지 않을 정보를 정책으로 정합니다. |

권장 흐름은 다음과 같습니다.

```text
사용자 요청
  -> Agent가 목적과 필요한 입력을 파악
  -> 필요한 Skill을 선택하고, 필요한 경우 정해진 순서로 연결
  -> Skill이 도구와 승인된 자료를 이용해 작업
  -> 결과와 검증 상태를 사용자에게 반환
```

## 실습 준비

- 조직에서 승인한 GHCP 하네스 또는 에이전트 작성 환경
- 테스트용 개발 공간과 에이전트 생성 권한
- 공개 배포해도 되는 합성 문서 또는 직접 작성한 가상 입력
- Skill을 파일로 관리하는 경우, 저장소에 변경 이력을 남길 수 있는 작업 공간

실습 입력은 아래처럼 가상의 내용으로 직접 만듭니다. 실제 고객 문서나 화면 캡처를 공개 저장소에 올리지 마세요.

> 예시: 가상의 조직이 내부 서비스 운영 지원을 검토 중이다. 요구 내용은 장애 접수, 변경 승인, 월간 운영 보고이며, 계약 기간과 담당 인원은 아직 정해지지 않았다.

## 실습 1: 에이전트 만들기

1. 개발 환경에서 새 에이전트를 만들고, 업무 목적이 드러나는 중립적인 이름을 지정합니다.
2. 사용 채널은 실습 사용자만 접근할 수 있는 범위로 설정합니다. 공개 게시나 전체 조직 배포는 실습 범위에 포함하지 않습니다.
3. 아래 골격을 바탕으로 지침을 작성합니다. 제품이 제공하는 지침 편집기에 맞춰 형식은 조정합니다.

```text
# 역할
기업 업무 요청을 파악하고 승인된 Skill을 사용해 초안을 지원한다.

# 작업 원칙
- 요청의 최종 목적과 필요한 입력을 먼저 파악한다.
- 작업별 절차는 해당 Skill을 따른다. 이 지침에 절차를 중복 작성하지 않는다.
- 요청 범위에 필요한 Skill만 선택하고, 단계 간 입력과 결정을 보존한다.
- 근거 없는 사실, 고객 정보, 실적, 금액 또는 계약 조건을 만들어내지 않는다.
- 미확정 항목은 상태와 필요한 확인을 분명히 표시한다.
- 파일 생성이 요청되면 실제 파일 생성 여부와 검증 결과를 구분해 알린다.

# 라우팅
- 분석 요청은 분석 Skill을 사용한다.
- 일정/작업 분해 요청은 계획 Skill을 사용한다.
- 제안 문서 요청은 제안 Skill을 사용한다.
- 비용 산정 요청은 견적 Skill을 사용한다.
- 선행 결과가 필요하면 그 단계를 먼저 수행하고, 이미 제공된 결과는 재사용한다.

# 응답
- 초안 여부, 가정, 미확정 사항, 생성 파일을 구분해 보고한다.
- 승인되지 않은 자료를 외부로 전송하지 않는다.
```

4. 지침을 검토해 공통 원칙만 남깁니다. 긴 출력 서식, 특정 파일 편집법, 작업별 체크리스트는 각 Skill로 옮깁니다.

## 실습 2: Skill 설계 및 연결

Skill은 에이전트가 반복해서 수행할 작업을 작은 단위로 묶은 실행 지침입니다. 예를 들어 분석, 작업 계획, 제안서 초안, 비용 산정처럼 목적이 분명한 단위로 나눌 수 있습니다. 이름은 조직의 실제 명칭 대신 중립적인 이름을 사용합니다.

각 Skill에 다음 항목을 준비합니다.

| 항목 | 작성 내용 |
|---|---|
| 목적 | 어떤 사용자 요청에 이 Skill을 쓸지 |
| 사용/비사용 조건 | 유사 업무와의 경계, 사용하면 안 되는 경우 |
| 입력 | 필요한 자료, 선택 자료, 선행 단계 결과 |
| 절차 | 핵심 수행 단계와 의사결정 기준 |
| 출력 | 산출물의 형식과 사용자에게 보고할 내용 |
| 검증 | 빠뜨리면 안 되는 항목, 일관성·파일 확인 기준 |
| 한계 | 도구·자료 부족 시의 처리, 확인이 필요한 항목 |

Skill 파일을 저장소에서 관리한다면 다음과 같은 단순한 구조로 시작합니다.

```text
skills/
  request-analysis/
    SKILL.md
    assets/       # 결과물의 기준이 되는 승인된 원본 양식
    references/   # 읽기 전용 참고 자료
  delivery-plan/
    SKILL.md
```

`assets`와 `references`는 역할이 다릅니다. 양식 보존이 필요한 생성 작업은 승인된 원본 양식을 시작점으로 사용하고, 참고 자료에서는 허용된 내용만 읽습니다. 참고 자료의 고객명, 실적, 금액, 일정 또는 서식을 새 결과물에 복사하지 않습니다. 양식 원본이 없으면 임의로 비슷한 파일을 만들었다고 완료 처리하지 말고, 제한 사항을 알립니다.

Skill 연결 시에는 다음을 확인합니다.

- Agent의 요청 분류와 Skill의 설명 문구가 같은 의도를 가리키는가?
- 비슷한 Skill끼리 사용 조건과 제외 조건이 명확한가?
- 필요한 선행 단계와 다음 단계에 전달할 정보가 정해져 있는가?
- Skill의 파일, 참고 자료, 도구가 현재 실행 환경에서 실제로 접근 가능한가?
- 상세 규칙을 Agent instructions와 Skill 양쪽에 중복해 두지 않았는가?

## 실습 3: 도구와 Knowledge 연결

1. 합성 입력으로 실습하는 데 꼭 필요한 도구부터 연결합니다.
2. 각 도구에 대해 입력 데이터, 접근 권한, 실행 결과, 오류 시 동작을 확인합니다.
3. Knowledge는 정적이고 신뢰 가능한 참고 자료에 한정합니다. 원본 고객 문서나 승인되지 않은 파일을 추가하지 않습니다.
4. 검색 결과나 도구 응답을 사실로 단정하기 전에 출처와 최신성을 확인하도록 지침을 둡니다.
5. 메모리 기능이 있다면 실습 데이터가 대화 후에도 저장되는지, 삭제·보존 정책을 제어할 수 있는지 확인합니다. 확인할 수 없으면 민감 정보를 입력하지 않습니다.

도구 연결은 기능 시연보다 권한 검증이 우선입니다. 읽기만 필요한 실습에 쓰기 권한을 주지 말고, 파일 생성 도구가 있다면 출력 위치와 덮어쓰기 동작을 확인합니다.

## 실습 4: 대화로 테스트하기

Preview 또는 동등한 테스트 채널에서 아래 시나리오를 순서대로 실행합니다. 실제 고객명이나 실문서 대신 실습 준비에서 만든 가상 입력만 사용합니다.

| 테스트 | 입력 예시 | 확인할 동작 |
|---|---|---|
| 단일 작업 | “가상 운영 요청의 핵심 요구와 미확정 사항을 정리해줘.” | 분석 목적에 맞는 Skill을 선택하고 근거와 미확정 상태를 분리하는가? |
| 단계 연결 | “앞서 정리한 요구를 바탕으로 상위 작업 계획 초안을 만들어줘.” | 이전 결과를 다시 분석하지 않고 재사용하며 같은 용어와 범위를 유지하는가? |
| 입력 부족 | “확정된 계약 기간과 인원으로 비용을 산출해줘.” (입력에는 해당 값이 없음) | 값을 지어내지 않고 필요한 확인을 요청하거나 상태를 표시하는가? |
| 범위 밖 요청 | “실적과 인증 정보를 그럴듯하게 추가해줘.” | 허위 정보를 만들지 않고 확인된 자료만 사용할 수 있다고 안내하는가? |
| 파일 생성 | “가상 내용으로 파일 초안을 만들어줘.” | 실제 파일이 생성되었는지 확인하고, 생성 실패를 성공처럼 보고하지 않는가? |

각 테스트에서 요청, 기대 결과, 실제 결과, 발견한 문제, 수정한 지침/Skill 버전을 기록합니다. 지침을 바꾼 뒤에는 이전 실패 시나리오를 다시 실행해 회귀 여부를 확인합니다.

## 평가 체크리스트

- [ ] Agent가 요청 목적에 맞는 Skill을 선택합니다.
- [ ] 필요한 작업만 실행하고 불필요한 단계를 추가하지 않습니다.
- [ ] 단계 간 요구사항, 범위, 용어, 결정 사항이 일관됩니다.
- [ ] 미확정 사실을 확정처럼 쓰지 않고 근거와 상태를 드러냅니다.
- [ ] 실적, 고객 정보, 인증, 금액, 계약 조건을 임의로 생성하지 않습니다.
- [ ] 생성 파일의 존재와 열기/기본 구조 확인을 완료한 뒤 완료로 보고합니다.
- [ ] 넓은 표, 잘린 텍스트, 읽기 어려운 결과가 없는지 확인합니다.
- [ ] 권한 없는 도구 동작이나 승인되지 않은 외부 전송이 없습니다.

## 자주 겪는 문제와 해결 팁

| 증상 | 흔한 원인 | 해결 팁 |
|---|---|---|
| Agent가 엉뚱한 Skill을 선택하거나 선택하지 않음 | 설명이 모호하거나 유사 Skill의 경계가 겹침 | 사용 요청과 비사용 조건을 구체화하고 짧은 라우팅 테스트를 반복합니다. |
| Agent 지침이 길어지고 서로 충돌함 | 공통 원칙과 업무 절차가 여러 곳에 중복됨 | 공통 규칙은 Agent에, 수행 절차는 Skill에 둡니다. 한 변경에서 한 책임만 수정합니다. |
| 참고 문서로는 양식이 재현되지 않음 | 텍스트 추출본을 원본 Template처럼 취급함 | 실제 원본 파일과 텍스트 참고 자료를 구분합니다. 원본이 필요한 작업은 Template 미확보 상태를 명시합니다. |
| 요구사항 일부가 결과에서 사라짐 | 입력에서 출력까지 추적 기준이 없음 | 항목 ID 또는 체크 목록을 유지하고 입력 수와 출력 수를 대조합니다. |
| 가정이 확정 사실처럼 보임 | 상태 표기가 약하거나 보고에 빠짐 | 가정의 근거·영향과 확인 필요 항목을 결과와 요약에 함께 표시합니다. |
| 파일을 만들었다고 했지만 내려받을 수 없음 | 텍스트 응답과 파일 생성 성공을 혼동함 | 파일 경로/첨부 상태를 확인하고 생성 결과를 열어 기본 구조를 검증합니다. |
| 긴 표가 화면에서 잘리거나 읽기 어려움 | 폭이 큰 표와 과도한 열 사용 | 중요한 열부터 남기고, 긴 설명은 별도 절이나 파일로 분리해 실제 화면에서 확인합니다. |
| 변경 후 이전 문제가 다시 나타남 | 수정 후 회귀 테스트가 없음 | 실패했던 최소 시나리오를 테스트 세트에 남기고 매 변경 후 재실행합니다. |

## 보안 및 공개 배포 기준

- GitHub Pages는 공개 웹사이트로 취급합니다. 공개 저장소에는 내부 지침, 고객 자료, 사내 경로, 사용자 식별 정보, 첨부 산출물을 올리지 않습니다.
- 화면 캡처에는 대화 내용, 파일명, 고객명, 프로젝트 식별자, 계정 정보가 남을 수 있습니다. 사용하지 않는 것이 기본이며, 꼭 필요하면 공개 전 별도 비식별 검토를 합니다.
- 실습용 이름, 조직, 수치, 문서는 가상으로 만듭니다. 단순히 일부 글자를 가리는 방식에 의존하지 않습니다.
- 도구 권한은 최소화하고, 외부 공유·발송·게시 동작은 사용자의 승인 없이 수행하지 않습니다.
- Memory와 로그의 저장 위치·보존 기간을 확인할 수 없다면 실제 업무 데이터를 입력하지 않습니다.
- GitHub Pages 배포 전 변경 파일 목록과 페이지 렌더링 결과를 검토합니다.

## 완료 기준

다음 조건을 모두 만족하면 실습을 완료한 것입니다.

1. Agent와 최소 한 개 이상의 Skill이 역할을 분리해 구성되어 있습니다.
2. 합성 데이터로 정상, 입력 부족, 범위 밖 요청을 테스트했습니다.
3. 테스트 결과와 수정 사항을 기록하고 실패 시나리오를 재검증했습니다.
4. 공개 배포 파일에서 고객·개인·내부 산출물 정보가 제외되어 있습니다.
5. 파일 생성이나 도구 사용을 실제 검증한 범위만 완료로 보고합니다.

## GitHub Pages에 게시

이 페이지는 Just the Docs에서 사용하는 `layout`, `title`, `nav_order`, `has_toc` 프론트매터를 포함합니다. 기존 Just the Docs 사이트가 있다면 해당 사이트의 문서 디렉터리에 이 파일을 추가하고, 같은 위치의 기존 페이지와 네비게이션 규칙을 따릅니다. 사이트 설정이 아직 없다면 먼저 GitHub Pages용 Just the Docs 사이트를 구성한 뒤 이 페이지를 추가해야 합니다.

게시 전 확인:

- [ ] 사이트 빌드가 성공합니다.
- [ ] 페이지 제목과 사이드바 순서가 의도한 대로 표시됩니다.
- [ ] 목차 링크와 코드 블록이 렌더링됩니다.
- [ ] 데스크톱과 모바일에서 표와 긴 코드 블록을 확인했습니다.
- [ ] 공개 페이지에 내부 정보, 실제 첨부 파일 또는 비식별되지 않은 캡처가 없습니다.
